# Monorepo layout

This is a pnpm workspace (`pnpm-workspace.yaml`, `packages: ["apps/*", "packages/*"]`) with eight members:

- **`apps/web/`**, the Next.js app (its own `package.json`, `env.ts`, `tsconfig.json`, `next.config.ts` + `config/`, one file per config key: `images`, `rewrites`, `redirects/`, `headers`, `experimental`, `build-id`, plus the ISR `cache-handler.js`, `drizzle/`, `src/`). It is **two layers, not one**. (1) The **API** under `app/api/**`, the only place that imports `@unicum.gg/core` by value (plus the non-page server routes: `opengraph-image.tsx`, `sitemap.xml`, auth), together with its API-side helper services (`services/{clans,players}/available-languages`, `clans/{detail,previous-clans,stronghold-leaderboard}`, `wargaming/wot/{clans,players}/top/by-language`, `coverage`, `tanks/marks-history`, `twitch`, `openapi`, `mcp`, `sitemap`; the ones using `next` APIs like `unstable_cache` stay here, never in core). (2) The **front**: `app/**/page.tsx`, `components/`, `hooks/`, `contexts/`, which fetches everything through the public API via `@unicum.gg/sdk` (`services/sdk`), server-side included. Pages never query the DB or WG directly; `import type` from core/services is fine (erased at build), value imports are not. Next memoizes identical SDK fetches within one render pass, so `generateMetadata` + the page body share a single request. **Page caching comes in two classes.** Catalog/leaderboard pages (home, players/clans landings, lang pages) are **ISR** (`force-static` + `revalidate`), so navigation serves prerendered HTML. Per-entity pages (player, clan, tank, vs, coverage) and pages reading `searchParams` (tanks index, stronghold) are **`force-dynamic`**; their caching lives in the endpoints, so the per-request cost is local HTTP hops onto cached payloads. **Builds are self-contained via the SDK loopback**: during `next build`, `services/sdk/loopback.ts` (side-effect import in the root layout, so server graph only) dispatches every SDK call to the in-process route handler of the commit being built (registry `local-routes.generated.ts`, filesystem-derived by `scripts/generate-local-routes.ts` on `predev`/`prebuild`/`postinstall`), so prerendered pages get real data from this build's own code and DB access, never from the deployed API (whose endpoints may lag one deploy behind). `buildSafe` (`services/sdk`) is only the last-resort net: if even the in-process handler fails (e.g. a DB-less build environment), the page prerenders as an empty shell and heals on its first revalidation; at runtime it propagates errors so a failed background revalidation keeps the last good page.
- **`apps/worker/`**, a standalone Node (`tsx`, no build) cron runner. `src/index.ts` sets `__dbContext = "background"`, installs the shutdown handler, and starts every cron group (the same sequence the web's `instrumentation.ts` used to run). Deployed as its own Coolify service; the web sets `RUN_CRONS=0` so only the worker executes crons.
- **`apps/bot/`** (`@unicum.gg/bot`), a standalone Discord bot on the `dixt` framework (`tsx`, no build). Slash commands live in `src/plugins/wot/commands/` (`/player`, `/clan`); both reply ephemerally with a "Share to channel" button and render stats as aligned code-block tables mirroring the site's tables (`lib/{table,stats-lines,clan-lines}.ts`). **The bot is a pure client of our own API through `@unicum.gg/sdk`** (`lib/sdk.ts`), zero `@unicum.gg/core`, zero direct DB access. Command data: `players(nick).detail()` / `clans(tag).{overview,stronghold,clanWars}()` (the endpoints handle the cold-DB resolve-on-WG case server-side). **Autocomplete**: `searchStream()`, respond with the first NDJSON chunk (the near-instant local DB hit, well inside Discord's 3s window) and abort before the slow WG chunk; input under the API's 3-char minimum falls back to the caller's Discord display name (players) or no suggestions (clans). Deployed as its own Coolify service (env `DIXT_*`, plus **`UNICUM_API_URL`** pointed at the internal API container so the SDK's calls stay on the Coolify private network; unset falls back to the public app URL). The shared env validation (via `APP_IDENTITY` → `@unicum.gg/shared/env`) still requires `DATABASE_URL`/`WARGAMING_APPLICATION_ID_*`/`CRON_SECRET` to be present even though the bot no longer uses them. Local dev: `apps/bot/.env.local` overrides `NEXT_PUBLIC_APP_URL=https://unicum.gg` so Discord can server-side-fetch the OG images (it can't reach localhost).
- **`apps/proxy/`** (`@unicum.gg/proxy`) is a tiny dependency-free HTTP CONNECT forward proxy (`tsx`, ~one file `src/index.ts`) that pins its egress source IP. It exists because our WG traffic must leave from Wargaming-whitelisted source IPs (each with its own G-Core per-IP budget), but a process inside a Docker bridge container cannot bind those public IPs (`EADDRNOTAVAIL`, and Docker SNAT rewrites the source anyway), so the pinning has to happen on the host. One instance therefore runs **per egress IP, on the host network** (via a Coolify **Docker Compose** resource with `network_mode: host`, since regular git apps can't get host networking: Coolify strips `--network=host` from custom options), each opening every CONNECT tunnel's upstream socket with `localAddress = EGRESS_IP`. It listens only on `BIND_ADDR` (the private Docker bridge gateway, e.g. `10.0.1.1`), never `0.0.0.0`, so it is not an open proxy on the public IP. The app side (`packages/core` wargaming client) puts the proxy URLs in `WG_EGRESS_*` and round-robins over them via undici `ProxyAgent`, and the transport keeps calling `api.worldoftanks.*` directly so the tunnel is transparent (TLS stays end-to-end). `compose.yaml` + `Dockerfile` live in `apps/proxy` (self-contained build context, zero workspace deps). The same pattern can host a remote APAC egress later (deploy an instance on an APAC VPS) to replace the archived `wg-asia-proxy`.
- **`packages/core/`** (`@unicum.gg/core`), all the backend + shared code, consumed via subpath exports (`@unicum.gg/core/db`, `/players`, `/clans`, `/discovery`, `/redis`, `/live`, `/cron`, `/wargaming/…`, `/lib/…`, `/constants/…`, `/env`). This is where nearly every former `src/services/*` lives now, plus `env` (via `@t3-oss/env-core`), the pure `lib/*`, and `constants/{rating,stronghold}`. Its `package.json` `exports` lists each folder-with-index explicitly (Turbopack's resolver ignores the array-fallback wildcard, so `@unicum.gg/core/db` etc. need explicit `"./db": "./src/db/index.ts"` entries). The **root barrel** (`@unicum.gg/core` → `src/index.ts`), historically empty, now re-exports the light, side-effect-free shared bits (currently `APP_IDENTITY`); core is being moved toward barrels, so it will grow, but it must never re-export a module that opens a pool/connection on import.
- **`packages/shared/`** (`@unicum.gg/shared`), the **client-safe, side-effect-free foundations** extracted from core so they can be imported anywhere (incl. browser bundles) without dragging the server stack. Deps: `@t3-oss/env-core`, `zod`, `@unicum.gg/wargaming`, `drizzle-orm` (schema/type inference only, no connection). **It is a clean acyclic leaf: zero `@unicum.gg/core` imports** (verified), so `core → shared` is one-way. Holds: `env`, `app-identity`, `constants/*`, `lib/{stats,bot-headers}`, **`db/schema`** (the drizzle table defs, `pgTable` opens no connection; the pool lives in core), the pure WoT domain math + types under `wot/` (`ratings`, `tank-stats`, `tanks/{meta,slug}`, `server-online`), `search` (SearchSource), pure `clans/*` + `players/*` logic/types (`snapshot-stats`, `ratings`/`computeClanRatings`, `tank-aggregate`, `derived-stats`, `lift-drag`, `vehicles`, `stats`, `twitch/live`, `clans/search-result`), and the full player-detail type cluster (`players/detail` = `PlayerDetailData`/stronghold modes/`EMPTY_CLAN_HISTORY`, `players/{stronghold-stats,rating-history}`, `clans/{ref,player-history}` = `ClanRef`/`ClanStint`/`PlayerClanHistoryFull`). `sideEffects` is `["**/env.ts"]` (only env-core validation runs at import). **Consumers import from the barrel**: `import { PlayerDetailData, computeClanRatings, env } from "@unicum.gg/shared"`, like wargaming, every folder has an `index.ts` and the root rolls them up (zero overlapping export names, checked). `package.json` exports is just `.` + the `./*` wildcard (core's internal type re-export wiring); intra-shared imports are relative. The drizzle table map is exported as a namespace from the barrel (`export * as schema` in `db/index.ts`), so core's `db/index.ts` does `import { schema } from "@unicum.gg/shared"` for `drizzle(client, { schema })`, no folder subpath needed. `apps/web/drizzle.config.ts` points at `packages/shared/src/db/schema/index.ts`. Mixed core modules (a client-safe type co-located with a server fn/fetcher) keep the fn in core and **re-export** the type from the precise shared subpath (never `export * from "@unicum.gg/shared"`, that would re-export the whole package), so existing `@unicum.gg/core/...` type imports still resolve.
- **`packages/wargaming/`** (`@unicum.gg/wargaming`), the neutral, publishable WG SDK (see [Wargaming SDK](#wargaming-sdk)).
- **`packages/sdk/`** (`@unicum.gg/sdk`), the fluent, typed client for **our own** public API, discord.js-style: `new Unicum().eu.clans("FAME").overview()`, `.eu.tanks("is-7").specifications()`, `.eu.players.top({ metric })`. **Both the response types and the fluent methods are generated from the served OpenAPI spec** (`pnpm --filter @unicum.gg/sdk generate`, which runs `generate:schema` then `generate:client`; both need the dev server up to read `/api/openapi.json`). `generate:schema` writes `src/generated/schema.ts` (via `openapi-typescript`, `date-time → Date`) and needs the dev server up; `generate:client` (`scripts/generate-client.ts`) writes `src/generated/client.ts` and reads the spec **from disk** (`apps/web/src/services/openapi/openapi.generated.json`, regenerated on predev/prebuild) so it can run even while the barrel points at a not-yet-generated client, falling back to the served URL. A new documented endpoint becomes a fluent method by "document it + regenerate", never a hand-edit. **The client is three files, split by who owns the code.** `runtime.ts` is the hand-written core (the lazy `RequestHandle` with its side-effect-free `.url()`, `buildUrl`, date-revival, the SSE + NDJSON transports, `UnicumError`, shared types, **and the SSE-subscription helpers** `subscribe{Player,Clan}Live`/`subscribeServerOnline`/`subscribeStreamersLive` + `ndjsonSearch` the generated client delegates to, that is where the one bit of per-endpoint logic the spec can't express, the `EventSource`/NDJSON URL template, lives). `generated/client.ts` is the fluent `Unicum` class, **generated in full** (100% machine output, never hand-edited). The model is a **denylist**: every documented endpoint is mapped to a fluent method UNLESS it is excluded, and **every exclusion is logged** (never a silent skip). Excluded are (a) **auto**, structurally not `await`-able JSON: `/sse` (SSE → `.live()`/`.online()`) and `/ndjson` (streams → `.searchStream()`), the only hand-written specials, wired from a small `RESOURCES`/`GLOBALS` config (name, key param, client class, root method, optional `namespaceRoot`/`liveHelper`/`searchStream`) that also gives region resources their ergonomic names; and (b) **manual**, an explicit list (currently the generic `/og` text card and `/mcp`, a POST JSON-RPC transport). Anything the generator can't place is logged as a loud **UNMAPPED** warning, not dropped. Signatures come straight from the spec: a query with **0 params** → `m()`, **exactly 1** → a bare positional arg (`search(q)`, `compare(names: string[])`, so removing the old hand-written `.search`/`.compare` regenerated them identically, zero call-site changes), **2+** → a `query?` object (`top(q?)`). **Array query params are honest arrays in the spec** (`names`/`tags` are `z.array`), serialized as CSV (`?names=a,b`) by the client's `querySerializer: { array: { style: "form", explode: false } }` (and `buildUrl`'s `String(array)` for `.url()`), matching the routes. The `/og/{region}/…` image paths are mirrored mechanically into an `unicum.og.eu.players("Animal")` prefix tree (url-only handles). Top-level GETs (e.g. `/health`) become `unicum.health()`. The generated file stays backtick-free pure structure (any `EventSource`/NDJSON URL template lives in the `runtime.ts` helpers it delegates to). `index.ts` is the barrel re-exporting the public surface (`Unicum`, `UnicumError`, `RequestHandle`, `UNICUM_API_URL`, and the public types). Non-2xx responses throw `UnicumError`. The default `baseUrl` is a relative `/api` in the browser (same-origin, no CORS) and `${APP_IDENTITY.URL}/api` (from `@unicum.gg/shared`) on the server, so it follows the environment with no hardcoded domain; override via `new Unicum({ baseUrl })`. Deps: `@unicum.gg/shared` + `@unicum.gg/wargaming` only, no `@unicum.gg/core`.

**Who consumes what.** Dependencies flow one way, no cycles:

| Package | Consumes | Consumed by |
|---|---|---|
| `@unicum.gg/wargaming` | (nothing internal) | `shared`, `core` |
| `@unicum.gg/shared` | `wargaming` | everything: `core`, `sdk`, web (client + server), `worker`, `bot` |
| `@unicum.gg/core` | `shared`, `wargaming` | **server code only**: `apps/web` API routes / pages / render services, `apps/worker`. Client components may import its **types** (`import type`, erased at build) but never values; the bot imports nothing from it. |
| `@unicum.gg/sdk` | `shared`, `wargaming` (types), our HTTP API | the web **front** (client components/hooks) and `apps/bot` |
| web public API (HTTP) | `core` (in its handlers) | `sdk` → front + bot, plus external users |

So data flows `WG → core (fetch/store) → web API → sdk → front/bot`, and client-safe types/math flow from `shared` into everything. Hand-written `fetch`/SWR fetchers against our own API are not allowed, go through the SDK.

The root `package.json` holds workspace config + thin scripts that delegate to `apps/web` (`pnpm --filter @unicum.gg/web ...`), so the `pnpm <cmd>` commands below run from the repo root. **Paths in this document that begin `src/...` are relative to `apps/web/`; backend code they refer to has usually moved to `packages/core/src/...` under the matching subpath** (e.g. `services/players/refresh-cron.ts` → `packages/core/src/players/refresh-cron.ts`, imported as `@unicum.gg/core/players/refresh-cron`).

# Database migrations

**NEVER suggest or run `pnpm db:push` (= `drizzle-kit push`).** The script is intentionally poisoned in `package.json` and will fail loudly. Reason: our `packages/core/src/db/schema/*.ts` files use a `makeXxxTable(region)` factory pattern (e.g. `playersByRegion = { eu: makePlayersTable("eu"), ... }`). Drizzle-Kit's AST analyzer only detects top-level `pgTable(...)` exports and cannot see tables hidden inside factory call bodies. `db:push` therefore concludes that every `eu_*`/`na_*`/`asia_*` table is orphan and emits `DROP TABLE ... CASCADE` for all of them. **This has already wiped the production DB once. Don't do it twice.**

The correct workflow for any schema change:

1. Edit `packages/core/src/db/schema/<file>.ts`
2. `pnpm db:generate` so drizzle-kit emits a new SQL file in `drizzle/000N_*.sql`
3. **Review the generated SQL.** If you see unexpected `DROP TABLE` on per-region tables, the factory pattern bit you again. Stop, do not apply, and write the migration by hand instead.
4. Apply via `psql "$DATABASE_URL" -f apps/web/drizzle/000N_*.sql`. Drizzle-kit tracks applied migrations in the `__drizzle_migrations` table on the DB; the `_journal.json` on disk is out of sync and is not authoritative.

# Big picture

## Per-region table factory

`packages/core/src/db/schema/*.ts` exports `makeXxxTable(region)` factories rather than top-level `pgTable(...)` calls. Every domain table physically exists three times (`eu_*`, `na_*`, `asia_*`). Consumers index into a `Record<Region, Table>` map (e.g. `playersByRegion[region]`). See the migration section above for the consequences.

## Connection budget

The Postgres server runs **`max_connections = 200`** (raised from the 100 default on 2026-08-20, when it ran full at 99 backends). It is **not a Coolify-managed database resource**, so the setting lives in the custom config in two places that must stay in sync: the `postgres_conf` column of `standalone_postgresqls` in `coolify-db` (the source of truth, rewritten into the file on deploy) and the mounted `/data/coolify/databases/<uuid>/custom-postgres.conf`. Applying a change needs a full container restart, a reload will not do.

The budget: **web 60** (`ecosystem.config.cjs` divides it across the PM2 cluster into `DB_POOL_MAX`), **worker 40** (`DB_BACKGROUND_POOL_MAX`, set explicitly on the Coolify service so a missing `NODE_ENV` cannot silently downgrade it), and the rest absorbs everything else pointed at this same server, because there is no dev database: the on-host `next build`, PR previews, every `pnpm dev` worktree, psql, drizzle-studio, backups.

Two things make reading `pg_stat_activity` misleading here. Connections arriving through the public port are SNATed by the Coolify proxy container, so every external client (all your dev instances, your psql) collapses into one `client_addr` and looks like a container: map the rest with `docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}} {{.GlobalIPv6Address}}{{end}}'`. And one process shows up under both its IPv4 and IPv6 address, so sum them.

`idle_timeout` (`packages/core/src/db/index.ts`) bounds the waste but does not shrink a busy pool: postgres.js round-robins FIFO over the open connections and restarts each one's idle timer on release, so a connection only expires when the pool is bigger than `requests/s x timeout`. Under steady traffic a pool sits at its historical peak concurrency. Size `max` accordingly. If 200 stops being enough, PgBouncer in transaction mode is the next step and the code is already compatible: `prepare: false`, no `LISTEN`/`NOTIFY`, no advisory locks (the cron lease is a table row).

## Cron loop

Crons run in the standalone **`apps/worker`** process (`src/index.ts`), which starts the groups below on boot. The web's `src/instrumentation.ts` keeps the same start sequence behind a `RUN_CRONS` gate (`RUN_CRONS=0` on the web service in prod → it skips them) plus a `globalThis.__cronStarted` HMR guard, so local `pnpm dev` can still run them in-process. A single `cron_leader` DB lease means **at most one instance ever executes a job** regardless of how many have it scheduled, so the worker and an un-gated web coexist safely (whoever holds the lease runs it). Every job is scheduled per region rather than globally, so a slow region cannot starve the others (EU's G-Core throttling used to cascade into NA/Asia skipping their ticks). The cron modules live in `packages/core/src/*` (paths below are the `@unicum.gg/core/...` subpaths).

| Cron | Source (`@unicum.gg/core/…`) | Cadence |
|---|---|---|
| `snapshot-pipeline-<region>` | `players/snapshot-pipeline` | Continuous per-region worker pool (not a scheduled tick): each worker claims a chunk of due players (adaptive cadence), gates the expensive per-account `tanks/stats` fetch on a cheap batched `account/info` change check, and writes only movers. Workers split into `backlog` (longest-overdue first) + `active` (freshest first) so the backlog drains without starving fresh players. |
| `player-cron-<region>` | `players/refresh-cron` | Every 10s. Drains the on-demand player refresh queue (page hits enqueue at priority 10). |
| `clan-refresh-cron-<region>` | `clans/refresh-cron` | Every 10s. Drains on-demand clan refresh queue. |
| `clan-backfill-cron-<region>` | `clans/backfill-cron` | Continuous (ticks every second, guarded against overlap; one pass is paced by the portal, not by the schedule). Re-fetches the oldest tracked clans (info, members, events, Global Map). Paced by the 1 rps clan portal that members/events go through. |
| `clan-stronghold-cron-<region>` | `clans/stronghold-cron` | Continuous per-region claim on `clans.stronghold_due_at`, at the cadence in `@unicum.gg/shared` `clans/stronghold-policy`: 6h for a clan that played in WG's trailing 28-day window, 3d dormant, 14d/30d for a fort that is unused or absent. Deliberately NOT in the backfill: the `wgsh-*` host is off both the portal budget and the G-Core-capped API budget, so coupling the two made a full sweep take days and left the clan page's 24h/7d columns diffing against baselines over a week old. |
| `discovery-cron` | `discovery/cron` | Weekly (Sundays 04:00) walk of clan member lists to find new account IDs. |
| `vehicles-cron` | `discovery/cron` | Daily (07:00) refresh of the vehicle catalogue from the IzeBerg/wot-src mirror. Runs after IzeBerg's typical push window (Tue/Thu 02:30-07:00 UTC, mostly ~04:30) so we never miss a release-day update. |
| `top-*-cron` | `wargaming/wot/{players,clans}/top/cron` | Nightly leaderboard precompute. The per-tank half streams `*_tank_snapshots` end to end, and fills `*_tank_stats` and the servers page's win-rate grid (`*_tier_winrate`) from that same walk. `pnpm --filter @unicum.gg/worker top-by-tank [region]` runs it by hand. |
| `changelog-cron` | `changelog/cron` | Daily at 18:00 Europe/Paris (`CHANGELOG_CRON` overrides, so weekly is a variable change). Posts the changelog digest to Discord, see [Changelog](#changelog). |
| `tank-ratings-cron` | `tanks/ratings-aggregate` | Half past the hour. Rolls the community votes into `tank_rating_aggregates` (shrunk means, spread, and the reputation-vs-results gap) and refreshes the voter brackets. Everything it does compares tanks to each other, which is the part a per-tank read cannot do; the tank pages themselves read live. |
| `server-online-cron` | `wargaming/wot/server/sample-cron` | Every 5 minutes, per region in one tick. Records each cluster's population into `*_server_online`, which is the entire history behind the servers section: Wargaming answers "how many are playing right now" and keeps nothing, so a tick that does not run is an hour of the curve no later run can recover. A failed fetch writes nothing rather than zeros, and the write is idempotent on (server, sampled_at). `pnpm --filter @unicum.gg/worker sample-servers [--watch]` runs it by hand. |
| `player-distribution-cron` | `players/distribution` | Hourly at :45, away from the coverage trends (:15) and the tank ratings (:30). Materialises `*_player_distribution`: the win-rate histogram plus one per rating metric (WN7/WN8/WNX, all four from a single `MATERIALIZED` scan of `*_players`, ~2.6s for EU) plus the per-tier and per-class battle shares (a ~1000-row aggregate of `*_tank_stats`, ~46ms). Read by the servers page and by every player page's percentile. |
| `streamer-reconcile-cron` | `twitch/reconcile-cron` | Daily (05:20). Realigns every `streamers.twitch_login` on the channel's immutable `twitch_user_id`, backfilling that id for rows seeded by channel name. The whole live path is keyed by login (Helix `user_login`, the badge href, the chat embed), and Twitch lets a streamer rename, so an unattended login either goes quiet (Helix returns nothing, the card just stops appearing) or starts lying (a freed login can be reclaimed by someone else, and we would show a stranger's stream under our player's name). `pnpm --filter @unicum.gg/worker reconcile-streamers` runs it by hand, which is worth doing right after seeding a batch so a typo surfaces instead of silently never rendering. |
| `tournaments-live-cron-<region>` | `tournaments/cron` | Every 5 min. Re-reads the catalogue's open statuses and re-mirrors every tournament that has not settled, so registration counts and a bracket in play stay current. A region carries a handful at a time. |
| `tournaments-archive-cron-<region>` | `tournaments/cron` | Half past the hour. Mirrors a bounded batch (40) of newly settled tournaments. Bounded on purpose: seeding the back catalogue is `pnpm --filter @unicum.gg/worker seed-tournaments` and is run deliberately, not left to an hourly job. |
| `onslaught-reconcile-cron-<region>` | `wargaming/wot/players/onslaught-cron` | Daily (05:50). Resolves the current nickname and clan of every ranked account by account id and materializes them onto the standings, so the board stays a pure DB read and a renamed player's link does not break. It also stamps the running season's codename and year, which is the half with a deadline: the client localization names only the current year, so a season that passes unstamped can never be named afterwards, and its successor loses the count it works its own position out from. |
| `onslaught-crest-cron-<region>` | `wargaming/wot/players/onslaught-cron` | Every 15 minutes, offset by two. Recomputes the Legend/Champion crest from the standings and the capture history onto the player row. Rode the daily reconcile first, and a day of lag was invisible everywhere the crest is worn except the one page that shows the current rank beside it, where a player who crossed into Legend that morning wore the wrong tincture under the right pill. Reads ~32,000 rows on EU (~230ms) and writes only what changed, so a settled archive costs one query. |
| `onslaught-watchdog` | `wargaming/wot/players/onslaught-watchdog` | Every 20 minutes, one global job. Alerts on Discord when the newest sample falls more than an hour behind, and again when it recovers, on the edges only. The capture runs in a separate service that serves no HTTP, so there is nothing to probe, and probing would answer the wrong question anyway: what matters is whether rows are still landing. It matters because the source publishes the current instant and keeps no history, so an hour nobody recorded is an hour no later run can go back for. |

## Changelog

The community Discord's `#changelogs` gets an automatic digest, written from the commit log by a model (`packages/core/src/changelog/`, `@unicum.gg/core/changelog`). The commits are read from the **GitHub API** (`compare/<last published sha>...HEAD`, the repo is public so no token), never from a local `git log`: the worker's container ships the built tree, not the repository. `write.ts` hands the subjects to OpenAI through the AI SDK (`generateText` + `Output.object`, schema `{ added, changed, removed }`) with one job the commit types could never do on their own: decide what was user-visible and say it in a player's words, dropping the refactors and the infrastructure. `message.ts` renders the fixed shape (`> **Update** (@here)`, `+` added / `~` changed / `-` removed, the site link), so the model only ever writes sentences. How far we published is the singleton `changelog_state` row (migration `0065`); a failed post leaves it untouched so the batch survives to the next tick, and a batch the model found nothing to say about is consumed anyway (else every later run re-reads it). **It was a Redis key first, and that is the one thing here that must not go back**: Redis survives a redeploy (the original reasoning) but not its own eviction policy, and the instance runs `allkeys-lru` at its 2 GiB ceiling, where a key with no TTL is evicted like any other. Read once a day, in a store shared with the ISR page cache, it was among the least recently used keys there. It was evicted between two runs, so the second read nothing, fell back to the 48h window and published the previous day's entries again (observed 2026-08-10/11). This value is not a cache: it is the only record of what the channel has already been told.

**Nothing here is maintained per feature.** A new page or section reaches the channel because it was committed.

It is also the one cron with a timezone (`scheduleCron`'s `options.timezone`, Europe/Paris): every other job is either paced or runs at an hour nobody reads, whereas this one is when a message appears in a community channel, so it must not drift with the clocks.

The cron only schedules when the bot, `OPENAI_API_KEY` and `DISCORD_CHANGELOG_CHANNEL_ID` are all set, and only in `NODE_ENV=production` (which `pnpm --filter @unicum.gg/worker start` sets, and which is the Coolify start command). That production gate is not cosmetic: `scheduleCron` skips the leader election in development, so a dev machine holding the same credentials (the local `.env.local` does) would publish the update itself. To run it by hand: `pnpm --filter @unicum.gg/worker changelog:dry` writes and prints it without posting or moving the marker, `changelog` (no `:dry`) posts it now. The `@here` only pings if the bot has Mention Everyone in that channel.

## Wargaming SDK

The `@unicum.gg/wargaming` package (`packages/wargaming/`) is a neutral, publishable, discord.js-style client. Construct once, navigate `wg.<region>.<surface>.<resource>.<method>({ ...objectParams })`, surfaces `api.wot.*` / `api.wgn.*` (folders `src/api/{wot,wgn}/`), `portal`, `stronghold`, `tournaments`, `source`; regions via `wg.eu`/`wg.na`/`wg.asia` (literal sugar) or `wg.region(r)` (dynamic). Every response type is modelled in full from the WG docs; `fields` is typed to the response's dotted paths (`FieldPath`/`Selected` in `src/fields.ts`) and narrows the return. Value-sets are real TS `enum`s. Deprecated-but-still-live endpoints are kept (WG's deprecation banners are unreliable). App-specific opinion (which `extra`/`fields` to request, camelCase mapping, `Date`, sanitize-html, portal hops) lives in the `apps/web`/`packages/core` facades, never the SDK.

**Import everything from the barrel**, not subpaths: `import { WargamingClient, Region, ClanRole, type PlayerInfo } from "@unicum.gg/wargaming"`. Every `.ts` file is reachable from `src/index.ts`, **zero files live outside a barrel**. The structure is **nested folder barrels**: each folder has an `index.ts` that `export *`s its children (`api/wot/index.ts` → the 9 resources, `api/index.ts` → `./wot` + `./wgn`, likewise `portal/`, `stronghold/`, `source/`, `client/`, `client/cache/`), and the root just rolls those up. The barrel exposes the **full** surface, including former internals (`Transport`, the rate-limiter defaults, `buildQuery`/`FieldPath`/`chunkArray`), the rule is "give the consumer everything", so barrels are plain `export *`, not curated. The modules have **no overlapping export names**, so the flat re-export is unambiguous, the one clash (`source/wot`'s client-tag `VehicleType` vs the encyclopedia's) was resolved by renaming the source one to `WotSrcVehicleType`; a future collision must likewise be renamed or explicitly re-exported. `source/wot/index.ts` is a pure barrel: its former content (the wot-src mirror config) moved to `source/wot/mirror.ts`. The `./*` subpath exports still exist for the package's own internal wiring (relative imports stay relative), but consumers use the barrel. This is safe for the front bundle because `package.json` has **`"sideEffects": false`**: Turbopack tree-shakes, so a component importing only `Region` (the common case, `Region`/`REGIONS`/`isRegion`/`regionFromPathname`/`REGION_*` are the most-used exports) does **not** pull `WargamingClient`, its transport/rate-limiter, or the `source/*` → `fast-xml-parser` chain into the browser. Verified: none of those ship to the client after the barrel migration. (In tsx-run consumers, bot/worker, there's no tree-shaking, so importing the barrel loads the client core at init, but those already load it through `@unicum.gg/core` anyway.)

The transport (`src/client/transport.ts`) wraps every call: injects `application_id` (three region ids from `env.ts`, required at boot) + default `language`, a per-region **token-bucket rate limiter** (`src/client/rate-limiter.ts`; defaults sit below WG's 20 RPS because traffic hits geo-routed G-Core CDN IPs that throttle harder, WG API EU=6 / NA=8 / Asia=8 RPS, clan portal 1 RPS/region), retries with i·i·2 backoff, and an embedded **response cache** (`src/client/cache/`, static-endpoint allowlist only, encyclopedia/glossary/types). Batched endpoints chunk to WG's per-request `account_id` limit and bisect on `INVALID_ACCOUNT_ID`.

There are **four limiter pools**, not two. `RateLimit.Stronghold` (5 RPS/region) is its own budget because `wgsh-*.wargaming.net` resolves straight to Wargaming and is not behind the G-Core WAF the other two are capped by (`api.worldoftanks.eu` lands on `*.fe.core.pw`), so it neither needs their ceiling nor should eat it. It replaced `RateLimit.None` on that host, which meant no bucket AND no egress lane: the calls left on the container's default IP at whatever rate the caller managed. `RateLimit.Tournaments` (3 RPS/region) is the fourth, for the tournament system on `worldoftanks.<tld>/tmsis/`: a third service again, behind the portal's Cloudflare rather than G-Core, and its own pool because the portal budget is 1 rps and already fully spoken for by the clan backfill, so borrowing it would make a catalogue sweep starve the clan cron (the exact coupling Stronghold was pulled out of). Like Stronghold it is **host-wide** rather than per-IP (`HOST_WIDE_POOLS`), so it is divided across egress lanes rather than replicated: the limit belongs to Cloudflare in front of a host we also fetch player marks from, and a block there would take those down with it. Non-2xx responses throw a typed `WargamingHttpError` carrying the status, which is what lets a resource treat a 404 as an answer rather than a failure, the stronghold host 404s for a clan with no fort, and the majority of clans have none.

**Both the cache store and the rate limiter are pluggable** so a multi-instance deploy shares one WG budget + cache. The SDK ships in-memory defaults; `apps/web/src/services/wargaming/` provides Redis implementations (`RedisCacheStore`, `RedisRateLimiter`, an atomic Lua token bucket) wired into the `wg` singleton via `getRedisClient()`, gated on `REDIS_URL` (absent → in-process fallback for local dev). Both fail open: a Redis blip degrades to "no cache" / "no shared limit", never a stalled WG call.

## Player page render path

`src/app/[region]/players/[nickname]/page.tsx` fetches one composite payload through the SDK (`unicum.region(r).players(nick).detail({ metric })`). The stale-while-revalidate flow lives in the endpoint (`loadPlayerDetailLive` in `@unicum.gg/core/players/detail`):

1. Read everything available from the DB (`loadPlayerInitialData`).
2. If we have at least the player row and the latest snapshot, respond immediately from cache and enqueue an on-demand refresh in the background.
3. If the DB is cold for that account, fetch live from WG and write back before responding, so the endpoint (and therefore the page and the Discord bot) works for any nickname WG knows. `account/info` gates the other WG fetches: WG's `account/list` can resolve a nickname whose info is null (an account locked by Wargaming), and the endpoint answers 403 `account_locked` for those (the page and the bot render a dedicated "account locked" state). 404 only when WG doesn't know the nickname at all.

`LiveSync` (SSE channel in `packages/core/src/live/`, bridged across processes via Redis pub/sub when `REDIS_URL` is set) lets the browser hot-swap fresh data without a manual reload once the background refresh lands.

**Marks and mastery ride the payload the profile already builds.** `buildPlayerMarkProgress` (`@unicum.gg/shared/players/mark-progress`) folds the vehicle rows into a tier-by-level breakdown for both Marks of Excellence and Mark of Mastery badges, and costs the endpoint nothing measurable (0-1ms in the perf trace): `vehicles` already carries `tier`/`mom`/`moe`, and the reach list reads `periodTanks.d30`, the per-vehicle 30-day diff the payload computes anyway. The one thing it adds is the region's Marks of Excellence bars, which is why `getTankMoeByRegion` now caches per region for 6h with in-flight dedup and a cron-driven invalidation: it was a full-table scan per call, harmless on the /tanks pages and not on the busiest endpoint we have. `getTankMomByRegion` got the same treatment for its own callers (the /tanks dataset and the per-tank page); the profile does not read it, since the mastery panel needs no thresholds. Both sit on `createRegionCache` (`@unicum.gg/core/lib/region-cache`) rather than a fourth hand-rolled copy of the TTL-plus-in-flight-dedup Map, and that helper counts generations so a refresh landing mid-read is not undone by the in-flight query writing its pre-refresh rows back with a full TTL.

Two measurement results shape what those panels are allowed to claim, both worth knowing before rebuilding either:

- **`max_xp` is not comparable to the mastery thresholds**, so there is no "distance to your next badge". The stored record score includes account bonuses (premium, first-win) while the badge is judged on the figure underneath: on a 950-vehicle garage, vehicles already holding an Ace average 1.86x the current Ace bar, and vehicles holding only 2nd class still clear it on every single one. The mastery panel therefore counts what was earned and explains the absence rather than estimating.
- **The Marks of Excellence comparison only holds within a tier.** Combined damage over the region's bar averages 1.6-2.3 across a whole garage regardless of the marks actually on the guns, which reads as "every gun clears every bar" and is purely an artifact of averaging ratios across tiers whose bars differ by an order of magnitude. Per tier the same data is sane (tier X: 1.07 on 3-mark guns, 0.98 on unmarked ones). So the panel compares each vehicle against its own bars and never aggregates the ratio.

**Every count in those tables is a link, and hovering one names the vehicles behind it.** A cell links into the Tanks tab as `?tier=<n>&moe=<0-3>` (or `&mom=<0-4>`), which meant teaching the shared `useTankFilters` two more filters. They ride the same pattern as the Common Test chip: optional fields on `FilterableTank` whose chip rows are absent rather than inert when nothing supplies them, so the catalogue never shows them. They are named `gunMarks`/`masteryBadge` there because the catalogue's own rows already use `moe`/`mom` for the region's thresholds, and the player table maps its rows across. The hover preview reads the tanks endpoint through SWR **keyed on the same URL the Tanks tab uses**, armed by the first hover rather than on mount, so the panel costs a profile view nothing and opening the tab afterwards reuses the response.

Because a mark is scored by Wargaming on a rolling window of recent battles that we cannot reconstruct, the reach list is framed as "vehicles whose average already clears a mark they do not carry", not as a progress bar: every entry clears its bar by construction, so a bar would be full on every row and carry nothing. The panel is laid out as the lift/drag panel above it (two counts side by side, then the vehicles worth acting on in two columns of the same icon-name-badge rows), and both counts are the profile's own stats table rather than a chart, since the site draws distributions as recharts histograms and tallies as tables.
## Tournaments

Wargaming runs tournaments continuously (nightly gold ladders, seasonal clan championships with cash prizes) through a **tournament system nothing else exposes**: `worldoftanks.<tld>/tmsis/api/v1`, public and unauthenticated, absent from the documented WG API, and rendered on their own pages by a client-side widget so no reader without JavaScript, and no crawler, ever sees a roster or a bracket. `packages/wargaming/src/tournaments/` models it (`wg.<region>.tournaments`), `packages/core/src/tournaments/` mirrors it into per-region tables, and the three documented endpoints below read only our copy, so a page view never waits on Wargaming.

**The join is the point.** Rosters carry `account_id`, so a tournament record hangs directly off the players and clans we already track: `GET /{region}/players/{nickname}/tournaments` answers a question Wargaming cannot, because their system is addressable only from the tournament's side and never from the player's. It surfaces as the profile's **Tournaments** tab (`/{region}/players/{nickname}/tournaments`), beside `/{region}/tournaments` and the per-tournament page that draws the bracket, the rosters and the placements.

**Two front-end traps, both already paid for.** `usePagination` treats a new array identity as a new list and resets its page DURING render, so a list built inline (`.filter()`, `.sort()`) hands it a fresh array every time and React kills the loop with "Too many re-renders": every list passed to it is memoized, and anything derived for a child that memoizes on identity (the placement and team-name maps) is memoized too. And `prizeTiers[].order` is the organiser's own numbering, which REPEATS (a live tournament ships 1, 2, 3, 4, 4), so it sorts the bands without identifying them and a React key on it collides.

**Two passes, because a settled tournament is immutable.** Its bracket, scores and rosters are finished history, so the archive is written once and then only read. `tournaments-live-cron` re-mirrors what has not settled; `tournaments-archive-cron` drains the settled tail in bounded batches. `detail_synced_at` is the state: the catalogue sweep sets the summary for everything it lists and CLEARS that stamp whenever a status changed, which is exactly when the bracket under it changed too, so a tournament mirrored mid-play is re-read once it completes rather than keeping its half-empty tree forever. Seeding the back catalogue is deliberate: `pnpm --filter @unicum.gg/worker seed-tournaments [eu|na|asia] [--limit N]`, interruptible and resumable (it claims only what is unstamped).

**The catalogue is not the archive, and on EU it is barely a sample of it.** The lobby endpoint reports 525 settled tournaments for EU, which is the ceiling on everything `sweepCatalog` can ever see, and we hold 540 (ten they have since dropped). But the ids are sequential per region, and they answer individually across the whole range: 866 consecutive ids probed over 2026 returned 866 tournaments, **none absent**, of which the catalogue listed 128. EU's ids run 5000000795 to 5000015165, so roughly **13,000 tournaments exist, are complete, and are reachable only by asking for them by id**. Nothing was deleted, it was dereferenced. NA and Asia are nearly whole from the catalogue alone (3,384 of ~4,188 ids, 2,030 of ~3,107), so this is an EU problem specifically, and it is why a player who remembers playing several finds one: their other entries are in tournaments the listing never mentioned. `enumerateRegion` (`@unicum.gg/core/tournaments/enumerate`) walks the id space instead, newest first, skipping what is already mirrored, via `pnpm --filter @unicum.gg/worker enumerate-tournaments [eu|na|asia] [--from ID] [--to ID] [--limit N]`. The region's floor is derived by truncating a known id (the region is the leading digit) rather than kept as a table of prefixes. Deliberate, not a cron: EU is a night of walking at the pool's three requests a second.

**Wargaming deletes the bracket of a routine tournament, so the mirror refuses to shrink one.** A day or two after it is played, a daily ladder comes back with its header and its rosters and an empty tree: EU's 3v3 N°26, 1v1 XI N°50 and Onslaught 5v5 N°26 of 30 August all answered with **zero stages** when refetched on 1-2 September, while the featured ones (the ONSLAUGHT 7v7 series, the Joust and the AMD qualifiers) keep theirs indefinitely. Our two passes walked straight into that: the live pass mirrors a tournament while it is being played, bracket and all, then it settles, the status change clears `detail_synced_at`, and the archive pass refetches it AFTER the purge. `mirrorTournament` replaced children unconditionally, so it deleted a finished bracket we had captured and wrote nothing over it, silently, days later, and only for the tournaments nobody else archives. So rosters are still replaced (a team that disbands must be able to leave the mirror) but the **bracket is refused when the incoming one would shrink what we hold** (`keepBracket`, on `heldBracket`'s stage AND match counts, since the purge is not all-or-nothing and a tree can come back with its stages and nothing under them). The consequence is deliberate: a bracket cannot be corrected downward. This also decides what the id-space recovery is worth, and it is worth saying plainly: the ~13,000 unlisted EU tournaments come back **without brackets**, because none exists upstream any more. What they do carry is the rosters, which is the join the whole section is built on. From here on the mirror is the only place these brackets survive at all.

**A tournament can exist with no dates, and storing that as 1970 is worse than skipping it.** The system sends `start_at: 0` / `end_at: 0` for a tournament created but never scheduled, and it is not only drafts: EU carries "OLS S7" at `upcoming` with eight teams registered, and "Spring Joust 2026 | 5v5 Play-off" at **`complete`** with four, both dateless. The SDK had an `at()` helper mapping `0` to null and `startAt`/`endAt` bypassed it, so those landed as January 1970. The visible damage is a listing sorted from 1970; the real one is that `isArchived` reads `end_at`, so an unplayed tournament reads as settled decades ago, is dropped by the live pass that should be watching it, and keeps an empty bracket for good once it is finally played. `startAt`/`endAt` are now `Date | null` in the SDK and `isScheduled` gates every write, with `mirrorTournament` returning **null** rather than throwing, since unscheduled is a state the system reports rather than a failure. Nothing is lost, which was checked rather than assumed: a dateless tournament carries no stages, so there is no bracket, no match and no result behind it.

**A missing tournament answers 200, not 404.** Asking for an id the system never issued returns `200 OK` with `{"status":"error","error_code":"NOT_FOUND"}` and an empty `data`, so `WargamingHttpError` never fires and the parser is handed `undefined`, which surfaced as a `TypeError` deep in the field mapping. That is unbranchable and, worse, indistinguishable from a genuine failure, which is fatal for a walk of the id space: the sequence has holes, and a run that cannot tell a hole from a blip either stops at the first one or silently skips real tournaments. The resource now reads its own envelope and throws a typed `TournamentApiError` (`isTournamentNotFound`), so the walk skips what is absent and leaves what merely failed unstamped for the next run. Checked in the resource rather than the transport because this host's envelope is its own: `error_code` as a flat string, against the WG API's nested `error.code`.

**"Settled" is not a status, and reading it as one breaks BOTH passes at once.** Wargaming abandons tournaments in a non-terminal state and never returns to them: Asia held fourteen sitting at `finished` since 2023 and 2024, and one at `running` three weeks after it ended. The status is honest for a live tournament (`finished` means results are still being settled, and on EU that really does take a day or two) but it is never revisited, so past a week it means nobody ever pressed the button. Keyed on `status = complete` alone, the archive never claimed those rows, leaving their page an empty bracket forever, while the live pass re-fetched a 2023 draw every five minutes for as long as the row existed, a cost that only ever grows. So the split is `status = complete OR end_at < now() - 7 days`, as ONE `isArchived` expression both pools read: they must stay exactly complementary, since any gap strands a tournament in neither pass or leaves it in both, and either only surfaces weeks later. `countPending` is scoped the same way, or a finished seed reports work left that it was never going to claim.

**Three traps the endpoints set, all of them silent.** (1) Every list pages at **ten** by default while reporting the real `total_count` in a field a naive caller never reads, so a 30-team bracket answers with its top ten and says nothing is wrong; `#getAll` asks for the max page and follows the count. (2) `page[number]`/`page[size]` are the only pagination names that work, and the obvious `page`/`per_page` are ignored *by returning page 1 again*, which reads as "no more results" rather than as an error. (3) What a standings row means depends on the bracket: a round robin fills the counters in, a single elimination records only a non-dense placement (1, 2, 4, 4, 8, 8, 8, 8) and leaves them at zero, and a **double elimination fills in neither**, only the seeding, so its finishing order has to come off the match tree.

**A team's clan is recovered, not given.** The tournament system knows teams and account ids and nothing else: a team is whatever name its captain typed, so a clan often plays under something unrecognisable (`OUUUH!`, `Last Try`, `1111`). But the accounts are ours, so `tournaments/clans.ts` matches each roster against clan membership and attributes the team when a quarter of the format's team size shared one clan. That is what `/{region}/clans/{tag}/tournaments` and the clan page's Tournaments tab read, and the join exists nowhere upstream.

Three things decide whether the attribution is honest. It resolves membership **as of the day the tournament was played** (`player_clan_history`'s `joinedAt`/`leftAt`), never the player's current clan: the archive runs back to 2018 and taking today's clan credits a 2019 result to whoever holds those players now. History covers 99.9% of the tournament accounts we track, so this is the accurate reading rather than the theoretical one. The quarter is measured against the **format**, not the roster we mirrored, because rosters are routinely partial and one account is always 100% of itself, which handed every phantom registration a clan with total confidence. And a team split evenly between two clans is attributed to **neither**, since picking one is picking whichever row the database returned first.

`clan_id`/`clan_members`/`clan_resolved_at` are denormalised onto the team row (migration `0094`) because answering "which tournaments did this clan enter" from the join would walk every roster in the archive on each page view. The stamp is what separates "no clan" (a real answer) from "not looked at yet", so `pnpm --filter @unicum.gg/worker backfill-team-clans [eu|na|asia]` is interruptible and resumable. `mirrorTournament` writes it AFTER its transaction and only logs a failure: the attribution is derived convenience and must never roll back a bracket that arrived intact.

**`extra_data.contacts` is never stored.** The endpoint returns it, but it is how a captain asked to be reached during their tournament (a Discord handle, a phone number), not something they published. The SDK carries it because the SDK is faithful to the endpoint; nothing downstream persists or renders it.

## Maps section

The `/[region]/maps` gallery + `/[region]/maps/[slug]` detail (EU shortcuts at `/maps` and `/maps/:slug`) are a **pure client-scripts encyclopedia, no DB and no WG API**: WG's `wot/encyclopedia/arenas` returns empty, so the catalogue is derived entirely from the two mirrors we already control (see [Wargaming SDK](#wargaming-sdk)). The pipeline mirrors tanks: SDK source resource (`packages/wargaming/src/source/wot/arenas.ts`, `SourceArenasResource`) enumerates arenas from `text/lc_messages/arenas.po` (`<id>/name` keys), reads each `scripts/arena_defs/<id>.xml` for the bounding box, `roundLength`, `vehicleCamouflageKind` and `gameplayTypes` (with base/spawn/control-point world coordinates), and keeps only arenas with a random-rotation mode (`ctf`/`domination`/`assault`); minimap PNGs come from the `wot.assets` mirror (`gui/maps/icons/map/<id>.png`, via `minimapUrl` in `@unicum.gg/shared`; WG's occasional filename typos are healed by `resolveMinimapBasename` against a live dir listing, `getMinimapBasenames` in core, rather than a hand-maintained alias table). Core (`@unicum.gg/core/wargaming/wot/maps`) dedupes arenas sharing a display name (keeping the shortest, canonical id), builds the slug index (name-based, like tanks), and exposes `listMapSummaries` / `getMapDetailBySlug` / `listMapSlugs`. The pure summary/detail builders + `MapGameMode`/`MapCamouflage` enums + `projectPoint` (world coords → minimap %) live in `@unicum.gg/shared/wot/maps`. The two API routes (`app/api/[region]/maps` + `[slug]`) are documented (tag `Maps`) so the SDK regenerates `unicum.region(r).maps.list()` / `.maps(slug).detail()`. Everything is heavily cached (static client data): the wot-src fetches for a day, the core catalogue in-memory per region, the pages ISR. The detail page's minimap overlays per-mode base flags and spawn points as absolutely-positioned markers.

**A map's variants are views of it, not maps beside it.** An arena named after another map and played in a mode of its own (`_wt` Waffenträger, `_ls26`/`_last_stand`, `_scc` Story Mode, `_comp7_nb` Onslaught night) is that map somewhere else: same place, own space, own rules. `variantOf(...).foldedIntoBase` folds every one of them onto the base map, where each becomes a view keyed by its battle type (`?view=waffentrager`), and `catalogFromArenas` keeps them out of `arenas`/the slug index and files them under `variantArenas`. `MapSummary.variants` carries what the gallery needs (arena, battle type, the minimap the variant's own layout resolved, its Common Test flag) so a tab draws the right image and links straight to the right view; `MapDetail.variants` carries the whole layout, since a variant is a full arena with its own play area, its own modes and possibly its own `comp7` (the night versions are exactly that). A map earns a tab by having the matching variant, appended by the catalogue layer like Clan Wars. The six slugs this retired (`steppes-waffentrager`, ...) were live and indexed, so `config/redirects` 301s each onto the view that replaced it.

Update 2.4 added the **night versions** of Sand River, Steppes, Glacier and Outpost (`nb` for night battle): the base map's Onslaught spawns on a 1 km area, with the two Comms Centers swapped for three Observation Posts. Points of Interest are typed by the client's own `POI_CONSTS` and named as the game names them: 1 Artillery Headquarters, 2 Comms Center, 3 Observation Post (`MapPoiType` in shared, raw number kept on the wire so a kind WG adds later still arrives).

**A variant's changes are recorded against it and read on the base map's page.** The readers resolve a folded arena to the map that carries it and re-key the field with `MAP_VARIANT_PREFIX` + the battle type, so a moved Observation Post reads as "(Onslaught Night)" instead of as a change to the Onslaught everyone plays, and the arena's arrival reads as "Waffenträger version added" instead of the map entering the game. `mapChangeArea` returns a key per space (the map, its Onslaught area, one per variant), which is a string rather than an enum because the variants are as open-ended as the battle types, and each area draws on its own minimap. The history keeps its original `pointsOfInterest:strike`/`:recon` keys, plus `:flare`, since rows are already recorded under them.

**Minimaps fall back to the test branch of the mirror, and that fallback is also the Common Test signal.** The live client can declare an arena whose space it does not ship (update 2.4 left ten in that state: the four night versions, three Waffenträger reskins and the three arcade minigames), so the live mirror branch 404s on them while the test one has the image. `ctMinimapUrl` rewrites a `wot.maps` URL onto `WG_CT`, and since the mirror publishes an image for every space the live client ships, *absent from `WG` and present on `WG_CT`* is exactly "declared but not carried". `findTestOnlyArenas` probes that for the whole catalogue while it builds (both halves matter: a live 404 alone would also catch the legacy arenas that have no image anywhere), eight at a time so the sweep does not reach the mirror as a burst, behind a per-region `inflight` (like the Clan Wars pool beside it) so a cold start runs one sweep rather than one per concurrent request, and the flag rides `MapSummary.commonTest` and each variant's own, picking the mirror branch for the image (either signal is enough: the probe fails towards "shipped", so the fold rule is what keeps a variant's minimap drawing through a mirror blip) and wearing the `CommonTestBadge` through `MapCommonTestBadge` beside the map's name, on the gallery card, on the variant's view pill and on the changes feed's rows, which read it off `ChangedMap.commonTest` and `.variantCommonTest`. It also **moves those maps' changes into the Common Test block** rather than marking them inline: a row about a space the live client cannot load has not shipped, whatever version its definition arrived in, so `getMapHistory` hands them back as `pending` and the feed's own reader (`maps/pending-read.ts`) reads them beside `map_test_changes`, scoped to those arenas rather than scanning the whole change log. With no test running the block carries no build number: the rows are pending because the client cannot load their space, which is true either way. Only an arena's newest recorded version moves, since the seasonal arenas really did ship in past years, and a presence row reads "Added on the test client" there. The probe fails towards "shipped", so a mirror blip cannot label a live map as test-only, and it clears itself the day the package lands.

## Servers section

The `/[region]/servers` page (EU shortcut `/servers`) is the game's clusters and how many people are on them: the live count, the population over 24h/7d/30d/1y stacked by cluster, the range's high, low and mean plus the all-time record, a weekly rhythm heatmap, and the three regions on one timeline.

**We are the archive.** `wgn/servers/info` answers the current instant and nothing else, there is no history endpoint, and nobody else archives the series, so every figure past the current minute exists only because `server-online-cron` recorded it into `*_server_online`. The history starts the day the sampler first ran and **cannot be backfilled**, which is why the cron writes nothing on a failed fetch (zeros are indistinguishable from a dead server and would drag every average through them for as long as the table lives) and why `sampled_at` is floored to the interval with a `(server, sampled_at)` primary key, so a re-run rewrites rather than doubles an instant.

**The cluster identity is Wargaming's own** ("EU1", "EU2", "203", "303", "501") and that is what is stored, compared and plotted. Wargaming names a region's first clusters and leaves the rest as bare identifiers, so `serverDisplayName` (in `@unicum.gg/shared/wot/server-stats`) continues the region's numbering for display: the hundreds digit is the region, what follows is the cluster, `203` shows as EU3 and `501` as ASIA1. The identifier stays visible on hover everywhere the label is shown.

**The label is derived from the identifier, never from the population**, and that distinction is the whole point. The read path used to sort the clusters by players online and number them from there, so "EU1" meant "the busiest one right now": on an evening when EU2 was ahead, EU2's figure was published as EU1's, and EU4/EU5 swapped whenever 204 and 205 traded places (observed live: 204 at 224 players while 205 held 2,374). Harmless in the top bar's tooltip, fatal for a recorded series, which would splice two servers together under one name. For the same reason the charts key their colours and their stacking order to the identity rather than to the rank, or a band would change hue whenever the ranking moved.

Reads live in `@unicum.gg/core/wargaming/wot/server/history` and group by instant first (`SUM` over one `sampled_at`) before aggregating over time, since a region total is a sum across clusters at one moment: averaging the clusters' own averages answers a different question the moment one appears or disappears mid-window. Timestamps cross the wire as epoch seconds and the rhythm's weekday/hour buckets are pinned to UTC, so nothing silently depends on the process's timezone; the heatmap shifts into the reader's own timezone on the client (`localRhythm` in `@unicum.gg/shared/wot/server-stats`), which is the only place the offset is known.

Two documented endpoints: `/{region}/server/stats?range=` (tag `Server`, beside the existing `/online/sse`) and the region-less `/servers/compare?range=`, since comparing EU, NA and Asia is not something one region can be asked for. The window parameter is `range` rather than `period` because the doc's defaults and examples are keyed by parameter name across the whole API and the leaderboards already own `period` with a different value set. The page is ISR (`force-static`, 5 minutes, matching the sampling interval) with the range switched client-side, so it needs no `searchParams`; the headline count bypasses all of it and arrives live over the SSE channel the top bar already uses.

The SDK gained a **region namespace** for this (`REGION_NAMESPACES` in `packages/sdk/scripts/generate-client.ts`): a region path naming no entity used to flatten into `unicum.eu.serverStats()`, and `unicum.eu.server` was a hand-written block in the template holding only `online()`. It is now generated, so `unicum.eu.server.stats(range)` and `unicum.servers.compare(range)` came from documenting the endpoints, with `online()` staying the declared SSE special.

**The page also carries the region's distributions**, which are about the playerbase rather than the clusters but answer the other half of the same question: the population says how many, the distributions say who. Win rate is drawn as a histogram, and beside it whichever rating metric the reader picked in the navbar: the panel reads the same `unicum.rating` cookie the selector writes and carries `RatingMetricInlineSelect` in its own heading, like the player page's progression chart. All three metrics are stored (`*_players` denormalises `wn7`, `wn8` and `wnx` alike, migration 0095), each with its own range, since WN7's scale stops around 1835 at the 99th percentile where WN8 and WNX run to ~2900. Bars are coloured by the site's own rating bands, and the battles are broken down by tier and by vehicle class. All of it is one materialised row per region (`*_player_distribution`, migration 0094, `@unicum.gg/core/players/distribution`, endpoint `/{region}/players/distribution`).

**What made it affordable is which table each half reads.** The histograms come off `*_players`, where win rate, WNX and the battle count are denormalised onto the player row, so the whole population is one sequential scan (2.1M rows, ~380ms on EU) instead of a pass over the 13M-row snapshots. The tier and class shares come off `*_tank_stats`, the ~1000-row per-tank aggregate the nightly cron already maintains, joined to `*_vehicles` for the tier and the class. **`*_tank_snapshots` is never touched** on the read path, nor by a cron of its own: it is 360 million rows and 85 GB for EU alone, which rules out anything keyed by what an individual player does per tier, however natural that question sounds.

Two scales meet here and must not be confused: `*_players.winrate` is a fraction and `*_tank_stats.winrate` is a percentage. The payload is fractions throughout, divided at the query. The shares are battle-weighted rather than averaged over vehicles, since tier VIII holds 250 tanks and six billion battles while tier X holds 125 and four, and the tanks nobody plays must not count like the ones everybody does.

**The win-rate grid is what that rule looks like when the question is asked anyway.** The page's last panel is what each rating band wins at each tier, the band down the side and the tier across the top, which needs precisely the per-player-per-tier record only the snapshots hold. It is not read from them. It is accumulated inside the nightly `top-players-by-tank` pass, the one job licensed to walk that table, which already streams it ordered by player with the player row joined on, so the whole grid costs four more columns in its SELECT and one map in memory (`@unicum.gg/core/players/tier-winrate`, written to `*_tier_winrate`, migration 0096, about three hundred rows per region). A feature that needs the snapshots joins the walk that exists rather than opening a second one.

The grid inherits that pass's rules rather than inventing its own: a vehicle counts once a player has a hundred battles on it, which is the leaderboard's floor and is what makes the grid describe the tiers as played by the people who play them, and an account counts from `DISTRIBUTION_MIN_BATTLES`, the histograms' own floor, so nobody is banded here who would not be counted there (a floor in common, not the same population: the grid additionally needs a vehicle really played, so it describes a subset). Cells are battle-weighted like the tier shares above them, and the two counters are stored rather than the ratio, so a cell can be re-summed instead of being an average of averages. The bands are read off `wn7Color`/`wn8Color`/`wnxColor` by walking the domain (`ratingBands` in `@unicum.gg/shared/wot/tier-winrate`) rather than copied into a table of thresholds, so moving one threshold cannot leave a stale copy behind. Each row then **stores the edges it was banded with** (`band_from`/`band_to`), like the distribution buckets beside it: membership is decided by the colour function at write time, so a threshold that moves at noon must not relabel rows that were filled at 03:30 under the old one. The axis is drawn from the stored edges, and falls back to today's only for a row written before the columns existed. Endpoint `/{region}/players/winrate-by-tier`, panel `components/servers/tier-winrate.tsx`.

`percentileOf` (in `@unicum.gg/shared/wot/player-distribution`) situates one account against the stored histogram, interpolating inside the bucket that holds it, which is what the player page's "Top 0.1%" reads. It is arithmetic over a payload that already exists, so a player's standing costs no query of its own.

## API documentation (OpenAPI)

The public API is documented with `next-openapi-gen` (config in `openapi-gen.config.json`). Flow:

- Each route's **response schema is co-located** in a `schema.api.ts` file next to its `route.ts`. The `.api` suffix is load-bearing: `next-openapi-gen` only scans `route.ts` plus `.ts` files whose name contains "api", so a plain `schema.ts` resolves by name but generates an empty body. These files are server-free (only `zod` + shared imports), so client components can import them too (the clan/player detail pages parse the response with the schema to revive `Date`s). Handlers return via `jsonResponse(schema, data)` (`services/openapi/json-response.ts`): it types `data` as `z.infer<schema>` so a drifting response is a compile error, and dev-validates the body. `src/services/openapi/schemas.ts` keeps only the **shared building blocks**: params/query schemas (`regionParams`, `searchQuery`, `playersTopQuery`, …), enum fields + the `assertEnumInSync`/`Exact` drift guards, and the shared row sub-schemas (`playerSummary`, `clanSummary`).
- Public route handlers opt in with a JSDoc block: `@tag`, `@pathParams`, `@queryParams`, `@response`, `@openapi` (referencing the exported schema names, resolved from the co-located `schema.api.ts` or from `schemas.ts`). `includeOpenApiRoutes: true` means only `@openapi`-tagged handlers are included, so internal routes (cron, discovery, og, md) are skipped automatically.
- `openapi-gen generate` writes `src/services/openapi/openapi.generated.json` (gitignored, regenerated on `postinstall`/`predev`/`prebuild`).
- `src/app/api/openapi.json/route.ts` serves that file, patching `servers`/`info` and running `normalizeParameters` (see gotchas). `Cache-Control: no-cache` so the docs never show a stale spec.
- `src/app/docs/page.tsx` renders the Scalar reference from `/api/openapi.json`, themed via `scalar-theme.css` (maps `--scalar-*` to the site's design tokens, so it follows light/dark). It is a full-screen overlay so the site nav/footer do not show.

Adding a public endpoint: write the handler, its Zod schemas, and the JSDoc block, then regenerate. Beware these `next-openapi-gen` quirks (all worked around in `schemas.ts` + `normalizeParameters`):

- **Enum values must be literal arrays** in `z.enum([...])`. It cannot read an imported array (`REGIONS`) or a native enum, so the literals are inlined and locked to their source enum by the `Exact<>` compile-time guard and the runtime `assertEnumInSync` (drift throws).
- **No template literals or non-literal expressions in `.meta()`**: the whole `.meta` is silently dropped. Use static description strings.
- **`.default()` on enum params is not serialized**: doc defaults live in `QUERY_PARAM_DEFAULTS` (sourced from app constants like `DEFAULT_RATING_METRIC`) and are applied per param name in `normalizeParameters`.
- **Enum params get wrapped in a single-element `allOf`**, which stops Scalar rendering a `<select>`; `normalizeParameters` flattens it.
- **A literal `example: "example"` placeholder** is injected on every param; `normalizeParameters` replaces it with the first enum value (so `region` prefills `eu`) or drops it.
- **Without `@tag`** the sidebar groups everything under the first path segment (`{region}`); tag handlers `Clans`/`Players`/`System`.

## Authentication (Better Auth + Wargaming.net ID)

Login is **Wargaming.net ID (OpenID) only**, via Better Auth. The instance lives in `packages/core/src/auth/index.ts` (`@unicum.gg/core/auth`), backed by the Drizzle adapter over the global `user`/`session`/`account`/`verification` tables (schema in `db/schema/auth.ts`, migration `0033`). WG isn't OAuth2/OIDC (the callback hands back the `access_token` directly, no code exchange), so it's a custom Better Auth plugin (`auth/wargaming.ts`): `/api/auth/sign-in/wargaming?region=<r>` starts the WG redirect, `/api/auth/callback/wargaming` mints a session via `handleOAuthUserInfo` + `setSessionCookie`. Users are keyed `<region>-<account_id>` with a synthetic verified email (WG returns none). The route handler is `app/api/auth/[...all]/route.ts`; the browser client + top-bar widget are `lib/auth-client.ts` + `components/login-widget.tsx`. `BETTER_AUTH_SECRET` is required on the **web** service only (optional in `env.ts` so the worker, which never imports the auth module, boots without it).

**The region is asked for, never inferred.** A WG account lives on exactly one region's account server, and the region a reader is browsing says nothing about which: a NA player reaches us through a shared EU link like anyone else, and sending them to `?region=eu` lands them on a login form their account does not exist behind (or, for the players holding an account on two regions, signs them into the wrong one). So every "log in with Wargaming" entry point on the site goes through `components/login-button.tsx`, which wraps the caller's own trigger (`asChild`-style, so each surface keeps its styling) and opens `login-modal.tsx`, the three-portal picker. The region is remembered in `AUTH_REGION_COOKIE` (`unicum.auth-region`, in `@unicum.gg/shared` because both sides need the name, distinct from `unicum.region`, which is only what the reader is browsing), so the picker opens on their own region next time and the server-side resume points that have no UI to ask in (`/api/connect/{twitch,discord}`, reached when the session is gone mid-flow) restart sign-in on the right portal via `lib/auth-region.ts`. **It is written by the callback, not by the click**: a player who picks the wrong portal, meets a login form their account does not exist behind and backs out would otherwise leave a year-long cookie naming a region they cannot log into, and the resume points would then trust it with no picker to correct them. The callback already knows the verified region (`prolongate` echoes back the account_id it is bound to), so what is stored is a login that happened rather than one that was attempted. Nothing writes `unicum.region` after login: the account's region and the data being read stay independent.

The modal also carries the reassurance block, which is not decoration: we are new, and we are asking a player to log in with the account they have spent years on, so the one screen that asks for that trust has to say where the password is actually typed. Each region therefore shows the portal host it hands over to (`REGION_PORTAL_HOST`, `eu.wargaming.net` and friends, the domain WG's `location` really redirects to, not the `worldoftanks.*` site), and the three lines below state only what a suspicious player can verify: the password is typed on WG's page and never reaches us, what comes back is a token that reads their own account data (encrypted at rest, silently prolongated by `auth/wargaming-token.ts` while the account stays linked, and used to act for them only where they set that up, as the clan boost workflow does), and the login code itself is linked on GitHub (the file, not the repository). Claim nothing there that the code does not do: the earlier wording said WG "only tells us which account is yours", which does not survive reading the file the line beside it invites you to open.

**`redirect_uri` carries no query string.** WG validates it and rejects any query ("Bad redirect_uri"), so the region and the post-login destination cannot ride along in the URL. Sign-in stashes them in a short-lived signed cookie (`wargaming_state`, `HttpOnly`, `SameSite=Lax`, 10 min). `callbackURL` is constrained to a same-origin relative path so it can't become an open redirect.

**Identity comes from WG, not the callback URL.** WG appends `status`/`access_token`/`account_id`/`nickname` to the redirect as *plain, unsigned* params (it isn't OIDC), so trusting `account_id` from the URL would let anyone forge a callback and take over any account. The callback instead verifies the token with WG (`wot/auth/prolongate`, which only succeeds for a genuine token and echoes back the account_id it is bound to) and derives identity from that response. The stored token is encrypted at rest (`account.encryptOAuthTokens`). Note `prolongate`/`logout` are POST-only on WG (a GET returns `ACCESS_TOKEN_NOT_SPECIFIED`, the token must be in the form body, never the query), which is why the SDK sends them via `wgFetch(..., { method: "POST" })`.

**Login-CSRF is blocked with a path nonce.** WG echoes none of our params back, but it appends its response to the redirect_uri *path* untouched, so sign-in mints a random nonce, puts it both in the signed cookie and in the redirect path (`.../callback/wargaming/<nonce>`), and the callback rejects unless the two match. An attacker can't forge the signed, `HttpOnly` cookie, so a login only ever completes in the browser that started it.

**Local testing gotchas** (two, both real, hit in this order):
- WG OpenID **rejects `http://localhost`** but **accepts `http://127.0.0.1` (loopback IP, even over http)**, the usual OAuth native-app rule. So test login on `NEXT_PUBLIC_APP_URL=http://127.0.0.1:3000` and browse via `127.0.0.1:3000`, not `localhost`. In prod the real `https://unicum.gg` domain works directly. The WG apps are type "Server" (IP-whitelisted, no redirect-URI config field), so the only redirect constraint is https-or-loopback, not a registered domain.
- Next dev is initialised on `localhost`, so it **blocks cross-origin dev requests from `127.0.0.1`**, HMR and every client fetch silently never fire, and interactive components (login widget, players-online) stay frozen on their SSR placeholder with no console error. Fix is `allowedDevOrigins: ["127.0.0.1"]` in `next.config.ts` (dev-only, already set). Verified end to end: the widget shows the nickname after the round-trip.

# Conventions

- Enums over union types or `as const` arrays. The codebase uses real TypeScript `enum` declarations consistently (`enum SortColumn`, `enum RatingMetric`, etc.).
- Keep files under ~400 lines. When one grows past that, extract a component/module into its own file instead of letting it sprawl.
- No section divider comments (e.g. `// ─── X ───`). Split the file instead.
- English only in code, comments, UI strings, and Intl locales.
- ESLint, not Biome. Never emit `// biome-ignore ...` directives.
- shadcn-style `src/components/ui/*` for primitives. Local components compose them, never reach into Radix directly.
- WG and G-Core failures are part of normal operation, not exceptions. The fetch and cron layers retry, bisect, and dequeue rather than throwing.
